# テリトリー散歩（仮） 設計書

## 1. 概要

歩いた軌跡で囲んだエリアを自分の「領土」として確定し、獲得面積の合計を
記録していく散歩ゲーム。今回作るのはMVP＝ソロ版のみで、以下5つの機能を
満たすことがゴール。

1. 地図表示
2. GPSモードでの現在地追跡・軌跡描画
3. テストモード（地図タップで軌跡をシミュレート、実機なしで動作確認できる）
4. 輪が閉じたら内側を領土として塗り、確定させる
5. 獲得領土の合計面積を表示・保持（アプリ再起動をまたぐローカル永続化）

対戦・他プレイヤーとの奪い合い・ログイン・サーバー同期は今回のスコープ外
（詳細は6章）。ただし、それらを将来足すときに大きな作り直しが要らない
程度には、データの持ち方を意識しておく。

## 2. 画面構成

今回は **1画面構成**（`WalkScreen` 1つ）で全機能を提供する。

```
WalkScreen
├── TerritoryMap（地図本体。軌跡・領土ポリゴン・現在地マーカーを描画）
└── ControlPanel（オーバーレイ。モード切替・スタート/ストップ・
                   輪を閉じる・合計面積表示）
    ├── ModeToggle（テスト/GPS切替）
    └── 統計表示（軌跡ポイント数・領土件数・合計面積）
```

理由: MVPは機能を検証する段階であり、画面遷移（履歴画面・設定画面など）を
先に作ると本質でない実装が増える。1画面に情報を集約した方が、プロトタイプ
（同じく1画面）からの移植もしやすい。

将来の拡張を見据え、`WalkScreen` は「地図」と「操作パネル」を別ウィジェットに
分けておく。これにより、将来 履歴画面・領土一覧画面などを追加する際に
`TerritoryMap` をそのまま再利用できる（Navigatorでの画面遷移を後から足しても
既存コードへの影響が小さい）。

## 3. データモデル

```dart
// lib/models/track_point.dart
// 軌跡上の1点。緯度経度と取得時刻を持つ。
class TrackPoint {
  final double lat;
  final double lng;
  final DateTime capturedAt;
}

// lib/models/territory.dart
// 確定済みの領土。輪を構成した点の配列と、その面積を持つ。
class Territory {
  final List<TrackPoint> points;
  final double areaSquareMeters;
  final DateTime closedAt;
}
```

合計面積（`totalAreaSquareMeters`）は `Territory` の配列から都度合計すれば
求まるため、独立した型は用意しない。永続化する値は以下の2つのみ。

```dart
// 永続化の対象（lib/storage/territory_repository.dart が扱う形）
{
  "territories": [ /* Territoryのリスト（points, areaSquareMeters, closedAt） */ ],
}
```

理由: 合計面積そのものを別途保存すると、`territories` との整合性が壊れる
リスクがある（保存し忘れ・計算式変更時の不整合等）。常に `territories` から
導出する一本の真実（single source of truth）にした方がシンプルで壊れにくい。

現在記録中の軌跡（`List<TrackPoint>`）は永続化しない。アプリを再起動したら
「歩いている途中の輪」は失われてよい仕様とする（MVPスコープでは許容範囲、
かつ実装がシンプルになる）。

## 4. アーキテクチャ

- **状態管理**: `provider`パッケージ。単一の `TerritoryWalkController`
  （`ChangeNotifier`）にモード・記録中軌跡・確定済み領土・合計面積をまとめる。
  理由: 画面数もロジックの複雑さも小さいMVPで、Riverpod/Blocのような
  ボイラープレートの多い仕組みを導入する必要性が薄い。プロジェクト規模に
  見合ったシンプルさを優先する。

- **フォルダ構成と責務分離**（詳細は `flutter-conventions` skill）:
  - `lib/models/` — データ型のみ
  - `lib/geo/` — 幾何計算・輪検出（Flutter非依存の純粋Dart）
  - `lib/state/` — Controller（状態とビジネスロジックの橋渡し）
  - `lib/location/` — GPS取得（`geolocator`パッケージのラッパー）
  - `lib/storage/` — ローカル永続化（`shared_preferences`を想定）
  - `lib/screens/` / `lib/widgets/` — UI

  理由: 幾何計算・GPS処理・描画を1ファイルに混在させると、後から
  「面積計算がおかしい」といった不具合を追うときに、UIコードを読み飛ばす
  手間が発生する。責務ごとに分けることで、`geo-math`・`territory-rendering`
  それぞれのskillとファイル群が1対1に対応し、Claude Codeが必要な部分だけを
  読みに行ける（トークン効率にも寄与する）。

- **永続化**: `shared_preferences` にJSON文字列として保存する程度で十分。
  サーバーへの同期は行わない。
  理由: ソロ版・端末単体で完結するスコープであり、SQLite等の重い永続化層は
  過剰実装になる。

## 5. コア処理のロジック（プロトタイプから移植する3つの計算処理）

詳細な数式・閾値は `.claude/skills/geo-math/SKILL.md` を参照。ここでは
考え方のみ要約する。

1. **距離計算（ハバーサイン公式）**: 2つの緯度経度から、地球を球体と
   みなした近似式で距離（メートル）を求める。GPSのブレ除去フィルタ
   （直前の点との距離が閾値未満なら無視）と、輪の自動クローズ判定
   （現在地とスタート地点との距離が閾値未満なら輪を閉じる）の両方で使う、
   このアプリの最も基礎的な計算。

2. **面積計算（靴ひも公式）**: 輪が閉じた瞬間の軌跡（緯度経度の配列）を、
   スタート地点を基準とした平面座標（メートル単位のXY）に変換したうえで、
   多角形の面積を求める。緯度経度のままでは平面図形の公式が使えないため、
   「局所的には平面とみなせる」という近似を挟む。

3. **輪の自動クローズ判定とGPSブレ除去フィルタ**: 新しい位置情報を1つ
   受け取るたびに、(a) 直前の記録点から近すぎればGPSのブレとして無視、
   (b) 一定数以上の点を記録済みで、かつスタート地点に十分近づいたら
   輪を閉じて領土として確定、の2段階の判定を行う。この2つの判定により、
   「歩いた軌跡が自然に閉じた領土になる」というゲームの中核体験が成立する。

## 6. 今回実装しない範囲と将来の拡張ポイント

今回のタスクでは以下を **実装しない**。

- 対戦機能（他プレイヤーの領土を歩いて奪う等のゲームルール）
- 他プレイヤーの領土・位置情報の表示
- ログイン・ユーザーアカウント
- サーバーとのデータ同期・バックエンドAPI

### 将来これらを足すときにネックになりそうな点

- **`Territory`に所有者情報がない**: 現状 `Territory` は「誰のものか」を
  持たない（ソロ版なので不要）。対戦機能を足す際は `ownerId` のような
  フィールド追加が必要になり、既存の永続化データ（JSON）のマイグレーションが
  発生する。今回はマイグレーション機構自体は作り込まない（オーバーエンジニアリング
  になるため）が、`territory_repository.dart` にJSONの読み書きを集約して
  あるので、将来の変更箇所はそこに閉じ込められる想定。

- **`TerritoryWalkController`が単一ユーザー前提**: 他プレイヤーの領土を
  同時に表示・更新するには、Controllerの設計を「自分の状態」と
  「他プレイヤーの状態（リアルタイム同期が必要）」に分割し直す必要がある。
  今回は単一のControllerにまとめる設計を選んでいるため、対戦機能追加時は
  ここが最も大きな設計変更ポイントになる。

- **ローカル永続化のみでサーバー同期の余地がない**: `shared_preferences`は
  端末ローカル保存であり、複数端末間の同期やサーバー側の権威データとの
  整合性は考慮していない。サーバー同期を足す際は、永続化層を
  `territory_repository.dart`の抽象（インターフェース）越しに差し替えられる
  ようにする必要があるが、今回はそのインターフェース分離まではやらない
  （YAGNI: 実際に必要になってから抽象化する）。

- **座標変換が局所平面近似**: `toLocalXY`によるメートル換算は、軌跡の
  スタート地点を基準にした近似であり、複数の領土やプレイヤー間で
  「同じ基準の座標系」を共有していない。対戦で領土の重なり判定（他人の
  領土と自分の領土が交差しているか等）をやるなら、共通の座標系・
  空間インデックス（例: geohash）の導入を検討する必要がある。
